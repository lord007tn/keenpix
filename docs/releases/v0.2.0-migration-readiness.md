# Keenpix Cloud v0.2.0 migration-readiness runbook

Status: preparation only — actual migration and cutover are deferred
Prepared: 2026-07-11
Scope: cloud-owned preparation and rehearsal for a later, separately authorized production migration
Source: `MIGRATION-PLAN-MASTER-TO-CLOUD.md`

## Safety boundary

This document does **not** authorize a migration, legacy access, a maintenance window, a data copy, a service restart, a DNS or proxy change, or a production cutover. Every operation that could read from, write to, stop, restart, or route traffic to or from legacy production requires a later, explicit owner instruction.

Until that instruction is received:

- do not connect to, query, inspect, test, restart, redeploy, reconfigure, or otherwise touch any legacy service, host, database, container, volume, route, or credential;
- do not resolve or probe legacy hostnames, and do not use legacy production for smoke tests;
- do not change public routing or DNS in preparation for cutover;
- do not copy production data into cloud resources;
- use only cloud-owned synthetic/test data for rehearsal;
- keep all legacy identifiers, endpoints, credentials, and commands out of source control and this runbook;
- treat every command-like block in this document as non-executable pseudocode.

The legacy environment must remain intact and untouched through the v0.2.0 release. Migration and retirement are separate owner decisions.

## Readiness decision

Migration readiness is currently **NO-GO**. The following gates from the master plan remain unresolved and must be closed under later authorization:

1. The exact legacy source release has not been proven with an immutable image digest and compatibility assessment.
2. Migrated API-key ownership metadata is not proven compatible with cloud authorization.
3. The existing migration utility's resume/checkpoint behavior can skip holes and is not approved for production.
4. A second-user disposition has not been approved.
5. Production write quiescence, final watermarks, and reconciliation have not occurred.
6. ClickHouse rebuild isolation and idempotency have not been proven in an authorized rehearsal.

No schedule may be set and no cutover may begin while any item above is open.

## Roles and separation of duties

Assign named people before any authorized rehearsal or cutover. One person may hold more than one role only if the owner explicitly accepts the reduced separation of duties.

| Role | Responsibility | Cannot self-approve |
|---|---|---|
| Owner/decision-maker | Grants scope, approves manifest, makes go/no-go and rollback decisions | Their own unreviewed technical evidence |
| Migration operator | Runs approved preflight, bounded copy, reconciliation, and target analytics rebuild | Reconciliation exceptions |
| Cloud operator | Controls cloud application, workers, cloud databases, and approved routing changes | Their own routing validation |
| Legacy operator | Performs only explicitly authorized legacy-side actions during the window | Expansion beyond the approved manifest |
| Product verifier | Verifies auth, SDK, transforms, dashboard, billing, email, and jobs | Operator assertions without evidence |
| Data verifier | Independently checks counts, bounds, identifiers, and checksums | Unexplained differences |
| Observer/scribe | Records commands, timestamps, output references, decisions, and incidents | Missing evidence after the fact |
| Security reviewer | Reviews secret handling, least privilege, and credential cleanup | Plaintext secret exceptions |

The go/no-go decision-maker and rollback decision-maker must be named explicitly. Operators must have a live communication channel and an agreed escalation path.

## Required approvals and prerequisites

### Authorization package

Before any legacy access, the owner must approve a time-bounded change request that states:

- the exact environments and resources in scope;
- the permitted read operations, write operations, service controls, and routing changes;
- the start and expiry time of the authorization;
- the named operators and approvers;
- the maintenance window and maximum permitted outage;
- the rehearsal or production purpose;
- the rollback authority and thresholds;
- whether source production data may enter the cloud target;
- whether the run is allowed to freeze writes;
- that no resource retirement is included.

Absence, ambiguity, or expiry of this package is an automatic stop.

### Technical prerequisites

All boxes must be checked with linked evidence before a live-source rehearsal can be proposed:

- [ ] Immutable source release identity captured under explicit authorization.
- [ ] Source release mapped to a Git commit or a signed compatibility assessment approved.
- [ ] Target commit and deployment digest pinned.
- [ ] Source and target schema/version preflight is fail-closed for unknown versions.
- [ ] Migration utility accepts immutable source/target fingerprints and a unique run ID.
- [ ] Every mutable table is copied inside explicit inclusive/exclusive time or key bounds.
- [ ] Resume uses per-table source-scoped checkpoints or idempotent keys, never a target-global maximum.
- [ ] API activity checkpoints are scoped to the intended key or organization.
- [ ] Mutable project and API-key state has a reviewed upsert contract.
- [ ] Cloud-only fields are preserved unless the manifest explicitly replaces them.
- [ ] API-key metadata receives the approved cloud organization ID without dropping compatible metadata.
- [ ] Owner, organization, second-user, session, and credential policies are explicit in the manifest.
- [ ] Dry-run is mechanically read-only.
- [ ] Each write phase is independently repeatable.
- [ ] Reconciliation reports source-window and target-window counts, bounds, distinct identities, and deterministic checksums.
- [ ] ClickHouse rebuild is isolated from cloud event ingestion and produces no duplicates.
- [ ] Coolify-managed backup status can be evidenced without repository-managed backup work.
- [ ] Rollback route and legacy recovery procedure are documented and independently reviewed.
- [ ] Monitoring dashboards and alert thresholds are ready before the window starts.

### Product and integration prerequisites

- [ ] Existing API-key behavior can be validated without revealing the key in output.
- [ ] Owner sign-in, organization membership, projects, API keys, and analytics have acceptance scripts.
- [ ] SDK and transform request contracts have saved, redacted expected results.
- [ ] Postmark has an authorized, nonsuppressed low-risk recipient for the cutover test.
- [ ] Polar production benefits and webhook verification are configured and independently checked.
- [ ] Google OAuth, if enabled for cutover, has a fresh secret in the approved secret store.
- [ ] Health, background jobs, cleanup jobs, queue behavior, and event ingestion have checks.
- [ ] Public SEO checks cover canonical URLs, redirects, robots, sitemap, schema, and representative pages.

## Migration manifest

The observer creates a manifest for each authorized run. The manifest is stored in the restricted evidence location, not in the repository, and contains no raw secrets.

Required fields:

- unique migration run ID;
- change-request and approval references;
- purpose: synthetic rehearsal, authorized live-source rehearsal, or production cutover;
- source fingerprint reference;
- target commit and deployment digest;
- encrypted secret references and expiry times;
- approved operator and verifier identities;
- source owner policy and target organization identifier;
- second-user disposition;
- sessions and credentials policy;
- included and excluded tables;
- per-table selection bounds and checkpoint strategy;
- project and API-key identifiers represented only by approved opaque references;
- cloud fields that must be preserved;
- reconciliation rules and checksum field sets;
- planned ClickHouse rebuild boundary;
- stop-write method and quiet-period duration;
- maximum cutover duration;
- go/no-go thresholds;
- rollback thresholds and route-recovery owner;
- evidence storage location and retention period.

Changing any manifest field after approval invalidates the approval unless the decision-maker records and signs an amendment.

## Safe cloud-only rehearsal

This is the only rehearsal permitted before later owner authorization. It must use cloud-owned synthetic/test data and isolated cloud resources. It must not imitate access to a legacy hostname or credential.

### Fixture design

Create a synthetic fixture set that includes:

- two synthetic users with an explicit keep/merge/exclude policy;
- one synthetic organization and membership set;
- projects with both mutable and cloud-only fields;
- an API key record with missing ownership metadata, then the approved repaired state;
- API activity at identical timestamps and across checkpoint boundaries;
- request logs with gaps, duplicate attempts, and out-of-order timestamps;
- hourly rollups spanning multiple time windows;
- empty, partial, interrupted, resumed, and already-complete target states;
- deliberately incompatible schema and source fingerprint cases;
- concurrent-looking target rows newer than the intended source window;
- analytics events suitable for detecting duplicate ClickHouse inserts.

Synthetic credentials must be non-secret, clearly labeled, and unable to authenticate outside the isolated rehearsal.

### Rehearsal stages

1. Provision an isolated cloud-owned rehearsal database and event store.
2. Record their creation evidence and confirm neither is connected to public traffic.
3. Load the synthetic source fixture and record deterministic fixture checksums.
4. Run fail-closed preflight against an incompatible fingerprint; verify that no writes occur.
5. Run dry-run against the valid fixture; verify that no target row changes.
6. Run a bounded initial copy with a synthetic rehearsal watermark.
7. Interrupt the copy at controlled checkpoints, resume it, and prove no holes or duplicates.
8. Add newer unrelated target rows and prove they cannot advance source checkpoints.
9. Re-run each phase and prove idempotency.
10. Apply the reviewed API-key organization metadata transformation and prove authorization scoping with synthetic credentials.
11. Verify mutable source fields update while declared cloud-only fields remain unchanged.
12. Reconcile every included table and require zero unexplained differences.
13. Stop isolated cloud event ingestion, clear only the isolated event target, backfill once, and reconcile aggregates.
14. Resume isolated ingestion and prove each new event appears exactly once.
15. Exercise every abort condition and verify the run stops without broadening writes.
16. Record stage duration, throughput, peak resource use, and evidence references.
17. Destroy or quarantine rehearsal data according to the approved cloud test-data policy.

### Cloud-only rehearsal acceptance criteria

- Unknown source or target fingerprints fail before writes.
- Dry-run changes zero rows and emits a complete proposed-operation report.
- Every selected row lies inside the declared source boundary.
- Interrupted/resumed and repeated runs produce the same final state.
- Target-global maxima cannot skip source rows.
- No duplicate identities, activity, request logs, rollups, or events remain.
- API-key ownership metadata resolves to the intended synthetic organization.
- Project and API-key mutable state matches the fixture contract.
- Declared cloud-only fields remain unchanged.
- Every critical-table count and checksum matches with zero unexplained differences.
- ClickHouse aggregates match the reconciled PostgreSQL basis exactly within documented transformation rules.
- No rehearsal resource receives public production traffic.
- Evidence contains no credentials, tokens, raw API keys, or personal data.

Before implementation, the security reviewer must verify that the real tool:

- refuses missing, expired, or mismatched authorization and manifest references;
- allowlists environments and resources instead of accepting arbitrary connection strings;
- prints fingerprints and redacted resource labels before confirmation;
- requires an explicit run ID and source-scoped bounds;
- cannot infer a production source from defaults;
- never logs connection strings, tokens, passwords, API keys, or decrypted secret values;
- separates dry-run and write-capable credentials;
- has per-table rate, timeout, and cancellation controls;
- emits an append-only audit record.

## Secrets and access handling

- Store secrets only in the approved secret manager or platform environment-variable store.
- Use separate, least-privilege, time-limited credentials for source read, target write, service control, routing, and verification.
- Never place credentials in shell history, command arguments visible to other processes, screenshots, tickets, chat, Markdown, Git, logs, or reconciliation output.
- Prefer secret-file descriptors or injected environment references that do not echo values.
- Redact database names, user identifiers, API keys, webhook secrets, email addresses, tokens, and connection strings from evidence.
- Confirm screen sharing and terminal recording cannot capture secret entry.
- Rotate or revoke temporary credentials immediately after the window or abort.
- Review access logs and record revocation evidence.
- If a secret appears in output, stop, restrict the evidence, rotate the credential, and record an incident before continuing.

## Authorized live-source rehearsal gates

This section becomes usable only after explicit owner authorization. It is still a rehearsal: it cannot change routing, freeze production writes, or represent cutover approval unless those actions are separately listed in the authorization.

Required sequence:

1. Verify the authorization package and manifest signatures.
2. Capture the approved immutable source fingerprint and compatibility evidence.
3. Confirm the target deployment fingerprint and isolated target boundary.
4. Run fail-closed schema/version preflight and mechanically read-only dry-run.
5. Copy only the manifest-bounded source window to the isolated target.
6. Reconcile identity, organization, project, API key, activity, rollup, and request-log data.
7. Validate application behavior in an isolated cloud session.
8. Rebuild the isolated event store with ingestion stopped and reconcile aggregates.
9. Record stage duration and forecast the maintenance window with safety margin.
10. Revoke credentials and return the environments to their pre-rehearsal state.

Zero unexplained reconciliation differences are allowed. A passing rehearsal is evidence for a later decision, not permission to cut over.

## Production cutover decision gates

The owner must issue a new, explicit production-cutover authorization after the live-source rehearsal passes. At T-24 hours, the decision-maker verifies:

- [ ] Authorized rehearsal passed with zero unexplained critical differences.
- [ ] Immutable source release and target deployment remain unchanged or were revalidated.
- [ ] Maintenance communication, start time, end time, and maximum outage are approved.
- [ ] Coolify-managed backup status is evidenced.
- [ ] Source write-freeze method and quiet-period measurement are approved.
- [ ] Final per-table bounds and checkpoints are recorded in the signed manifest.
- [ ] API-key ownership repair is reviewed and has a real verification procedure.
- [ ] ClickHouse ingestion-stop, clear, backfill, and resume procedure is reviewed.
- [ ] Routing change and independent TLS/origin verification are approved.
- [ ] Rollback routing and legacy recovery owners are available.
- [ ] Postmark, Polar, OAuth, workers, jobs, and health prerequisites pass.
- [ ] Monitoring and evidence capture are live.

Any unchecked item is a no-go.

## Authorized cutover sequence

This section is a checklist for a later owner-authorized window. It must not be executed during v0.2.0 release work.

1. The observer records the approved run ID, start time, participants, source fingerprint, and target fingerprint.
2. The legacy operator performs the approved write-freeze action while leaving rollback resources intact.
3. The data verifier confirms activity timestamps and counts stop advancing for the approved quiet period.
4. The migration operator records final per-table bounds and the cutover watermark in the restricted manifest.
5. The migration operator runs the final bounded delta through the approved upper bound.
6. The migration operator applies the approved organization metadata and mutable-state upserts.
7. The data verifier independently runs reconciliation. Any unexplained difference is an immediate no-go.
8. The cloud operator stops cloud event ingestion, clears only the approved target event set, and starts one bounded backfill.
9. The data verifier reconciles target event aggregates against reconciled PostgreSQL data.
10. The cloud operator starts the approved cloud application and workers and verifies health before routing.
11. The decision-maker reviews all evidence and gives a recorded go/no-go decision.
12. Only after recorded GO, the cloud operator performs the exact approved routing change.
13. The product verifier runs the production smoke-test checklist.
14. The observer starts the defined observation window and records every alert and decision.

No legacy resource may be retired, destroyed, reconfigured beyond the approved window, or used for unrelated testing.

## Data reconciliation acceptance criteria

For every included dataset, record source selection bounds, target selection bounds, row count, minimum and maximum ordering value, distinct parent identifiers, deterministic checksum fields, and exceptions.

| Dataset | Required acceptance |
|---|---|
| Users and identities | Approved identities exist exactly once; second-user policy applied; sessions excluded unless explicitly approved |
| Organizations and membership | Owner and memberships resolve to the approved cloud organization with correct roles |
| Projects | Identity and mutable fields match; cloud-only settings are preserved per manifest |
| API keys | Existing key relationship, counters, last-request state, and compatible metadata match; cloud organization metadata is present; no key value is exposed |
| API-key activity | Window count, bounds, key-scoped checkpoint, and deterministic checksum match |
| Hourly rollups | Every selected bucket and measure matches exactly within the declared transformation contract |
| Request logs | Window count, bounds, distinct project/key counts, and deterministic checksum match; no holes or duplicates |
| ClickHouse events | Aggregate count and dimensions match the reconciled PostgreSQL basis; each event appears once |

Acceptance rules:

- Critical identity, project, key, activity, rollup, request-log, and event differences must be zero unless the signed manifest contains a field-level transformation rule.
- Every permitted transformation must include input, output, reason, expected count, and independent approval.
- Sampling may supplement but never replace full counts and checksums for critical datasets.
- Reconciliation evidence must be reproducible and redacted.
- Unknown, missing, extra, or out-of-window rows are failures, not warnings.

## Abort and rollback gates

Abort before routing if any of the following occurs:

- authorization, manifest, fingerprint, schema, or version mismatch;
- source writes fail to become quiescent within the approved time;
- a step exceeds its approved duration or resource threshold;
- a copy or reconciliation phase errors, skips a checkpoint, or produces a duplicate;
- any unexplained count, bound, identity, relationship, or checksum difference;
- API-key organization metadata is missing or authorization fails;
- cloud-only fields are overwritten outside the manifest;
- ClickHouse ingestion cannot be isolated or aggregates diverge;
- a secret is disclosed or a credential behaves outside least privilege;
- health, Postmark, Polar, OAuth, worker, queue, or job prerequisites fail;
- an operator cannot identify the exact resource before an action.

Roll back after routing if any of the following occurs:

- sustained 5xx or authorization failures exceed the approved threshold;
- existing API or SDK contracts break;
- transform correctness or origin/allowlist behavior regresses;
- events are missing or duplicated;
- auth, organization, dashboard, project, or API-key access fails;
- queue, jobs, email, billing webhook, or health behavior is materially impaired;
- TLS or routing does not match the approved origin behavior;
- the maximum cutover duration expires without full acceptance.

Rollback is a controlled restoration of the approved legacy route and service state. It must preserve cloud imports and logs for diagnosis and must not attempt destructive reverse synchronization. If cloud-only writes occurred, record them and require a separate reviewed reconciliation plan.

## Post-cutover verification

Run immediately after authorized routing and again during the observation window:

- [ ] Public and API hostnames have valid TLS and resolve to the intended origins.
- [ ] Canonical redirects preserve paths and queries where required.
- [ ] Existing API key succeeds without exposing it in evidence.
- [ ] SDK authorization, transform output, project allowlists, caching, and error contracts match approved expectations.
- [ ] Owner sign-in, organization membership, dashboard, projects, API-key visibility, and analytics work.
- [ ] A new request produces exactly one expected record/event across the designed stores.
- [ ] Queue and scheduled/background jobs are healthy.
- [ ] Postmark sends one authorized low-risk message and records delivery.
- [ ] Polar webhook signature verification and entitlement behavior pass.
- [ ] OAuth, if enabled, follows the approved production-domain flow.
- [ ] Health endpoints and dependency checks pass.
- [ ] Public SEO endpoints, canonical tags, robots, sitemap, schema, OG images, and representative content return expected results.
- [ ] Error rate, latency, authorization failures, transform success, and event parity remain within thresholds.

Monitor intensely for the first two hours and maintain heightened review for 24–48 hours. Keep legacy resources recoverable and unchanged until the observation window closes and the owner separately approves retirement.
