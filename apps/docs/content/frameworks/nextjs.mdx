`next/image` lets you swap its optimizer for a custom loader. Point it at Keenpix and keep
using `<Image>` exactly as before — Next still generates the `srcset`, Keenpix serves
each width.

**Use this setup when you want image transformation and delivery to remain separate from
the Next.js server or hosting platform.** Keep the built-in optimizer when it already meets
your deployment, cache, and cost requirements. A custom image CDN adds another service
boundary, so the gain must justify the URL migration, cache policy, and failure mode.

<Callout title="Published 0.3.2 installation caveat">
  The 0.3.2 npm tarballs currently contain unresolved `workspace:^` dependencies.
  If installation fails with `EUNSUPPORTEDPROTOCOL`, use the "Without the package"
  loader below until corrected packages are published.
</Callout>

## 1. Install the package

```bash
pnpm add @keenpix/next
```

## 2. Add a global loader

```ts
// keenpix-loader.ts
'use client'

import { createManagedKeenpixConfig, createNextLoader } from '@keenpix/next'

export default createNextLoader(createManagedKeenpixConfig('YOUR_PROJECT_ID'))
```

Register the file relative to your project root:

```ts
// next.config.ts
import type { NextConfig } from 'next'

export default {
  images: {
    loader: 'custom',
    loaderFile: './keenpix-loader.ts',
  },
} satisfies NextConfig
```

The global loader works with App Router Server Components as well as Client
Components. Keep the project id public; never place a signing secret in this file.

## 3. Use `<Image>` normally

```tsx
// app/page.tsx
import Image from 'next/image'

export default function Hero() {
  return (
    <Image
      src="https://assets.example.com/hero.jpg"
      width={1200}
      height={800}
      alt="A mountain at sunrise"
      sizes="(max-width: 768px) 100vw, 50vw"
    />
  )
}
```

<Callout>
  Every `src` must be an absolute URL on a host in your project's origin allowlist
  (**Settings > Security**). Add `assets.example.com` for these examples. Relative
  paths such as `/hero.jpg` are rejected with HTTP 400 by managed delivery.
</Callout>

## Set `sizes` for responsive layouts

The loader receives each width that Next.js puts into the generated `srcset`. The browser
still needs an accurate `sizes` value to choose among those candidates. Without it, a
responsive image can be treated as viewport-wide and download more pixels than its actual
slot needs.

```jsx
<Image
  alt="Canvas backpack in olive green"
  height={1200}
  sizes="(max-width: 768px) 100vw, 50vw"
  src="https://assets.example.com/products/backpack.jpg"
  width={1600}
/>
```

Keep width candidates aligned with real component breakpoints. More variants are not
automatically better: they create more cache keys, and adjacent widths that produce almost
the same byte size add little value.

## Quality on current Next.js

These examples use quality 75, the default. Next.js 16 defaults
[`images.qualities`](https://nextjs.org/docs/app/api-reference/components/image#qualities)
to `[75]`; its built-in optimizer selects the nearest allowed quality. Custom
loaders receive the requested quality directly, so do not rely on snapping in
this integration. If you need other values, add them to `images.qualities` in your existing image configuration, for
example `qualities: [60, 75, 90]`, and choose one of those values on `<Image>`.

## Per-image transforms in a Client Component

`createNextImageProps` includes a `loader` function. Call it inside a Client
Component so that function does not cross the Server Component serialization
boundary. Use the global loader above for ordinary Server Component usage.

```tsx
// app/transformed-hero.tsx
'use client'

import Image from 'next/image'
import { createManagedKeenpixConfig, createNextImageProps } from '@keenpix/next'

const keenpix = createManagedKeenpixConfig('YOUR_PROJECT_ID')

export default function TransformedHero() {
  return (
    <Image
      {...createNextImageProps(keenpix, {
        src: 'https://assets.example.com/hero.jpg',
        alt: 'A mountain at sunrise',
        width: 1200,
        height: 800,
        sizes: '(max-width: 768px) 100vw, 50vw',
        quality: 75,
        fit: 'cover',
      })}
    />
  )
}
```

## Without the package

For managed delivery, you can replace `keenpix-loader.ts` with this minimal loader
and keep the same `next.config.ts` registration and absolute sources:

```ts
// keenpix-loader.ts
'use client'

import type { ImageLoaderProps } from 'next/image'

export default function keenpixLoader({ src, width, quality = 75 }: ImageLoaderProps) {
  const params = new URLSearchParams({ w: String(width), q: String(quality) })
  return `https://cdn.keenpix.com/p/YOUR_PROJECT_ID/img/${encodeURIComponent(src)}?${params}`
}
```

## Static export and non-Vercel deployments

A custom loader returns ordinary external image URLs, so it also works when Next.js emits a
static export and no Next.js image-optimization server exists at runtime. Keenpix still has
to be reachable from the browser. Continue to use absolute, allowlisted source URLs.

For managed delivery, the public project id belongs in the
`cdn.keenpix.com/p/<project-id>` path. It is routing context, not a secret. For self-hosting,
the project query parameter selects the project on your own image host. The transform URL
concepts are similar, but moving between the two paths still requires hostname, cache, and
configuration planning.

## Protect the source and URL grammar

Keenpix only fetches from hosts in the project's origin allowlist. Start with the narrowest
set of source hosts your application actually uses and verify that an unapproved host fails.
The fetcher also blocks private/internal addresses and revalidates redirects, but the
allowlist remains the first product-level boundary.

Do not put an HMAC signing secret in `keenpix-loader.ts`; the loader is browser-facing. If
your project requires signed transform URLs, sign them on a server you control or route the
request through a server-side signing endpoint. Signatures are useful when third parties
could append parameters and create expensive cache misses. They do not stop someone from
copying and replaying an already valid public image URL.

## Validate the integration before launch

Check the result as a delivery pipeline, not only as a rendered image:

1. Inspect the final `<img>` and confirm `srcset` contains several Keenpix URLs with
   different `w` values.
2. Resize the viewport and verify the browser selects a candidate appropriate to the
   rendered slot.
3. Check `Content-Type`, `Vary`, and `Cache-Control` on AVIF, WebP, and fallback responses.
4. Confirm an unapproved source host is rejected.
5. Compare decoded output and transferred bytes with your own source files and settings.
6. Test an uncached request, a repeat request, an origin failure, and the rollback path.

`fmt=auto` varies the response by the browser's `Accept` header. Every cache in front of the
image service must keep those variants separate. If the outer CDN cannot vary safely, use
explicit AVIF/WebP URLs and provide a fallback through `<picture>` instead.

## Decide on cost and ownership

Next.js and Vercel's built-in image optimization can be the simplest option because there
is no new provider or URL migration. Keenpix is a better candidate when the team wants one
image URL grammar across frameworks, a separately measured delivery layer, published
managed-delivery allowances, or a future self-host path. Neither architecture is
universally cheaper or faster; model requests, cache reads/writes, delivered bytes, origin
behavior, and engineering time from your own workload.
